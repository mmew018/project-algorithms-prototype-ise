# ISE Prototype User Test Plan

ผลในเอกสารนี้เป็น **เกณฑ์เป้าหมาย** จนกว่าจะมีการทดสอบกับผู้ใช้จริง

## เป้าหมาย

- ตรวจว่าเส้นทาง Search → Understand → Rank → Explain ใช้งานและเข้าใจได้
- ตรวจว่าผู้ใช้ค้นหา กรอง และเปรียบเทียบได้โดยไม่ต้องมีผู้ช่วย
- ตรวจว่าผู้ใช้เข้าใจว่า Match Score ไม่ใช่ AI accuracy
- ตรวจว่าผู้ใช้ทราบว่าราคาและข้อมูลเป็นชุดสาธิตแบบคงที่

## ผู้เข้าร่วม

- แนะนำ 8 คน ขั้นต่ำ 6 คน อายุประมาณ 18–35 ปี
- เคยค้นหาหรือซื้อสินค้าไอทีในช่วง 12 เดือนที่ผ่านมา
- มือใหม่ 3 คน ระดับกลาง 3 คน และ Tech-savvy 2 คน
- ไม่ใช่ผู้พัฒนาระบบและไม่เคยเห็น ISE มาก่อน
- แบ่ง Desktop และ Mobile ให้ใกล้เคียงกัน
- เก็บเฉพาะ Participant ID, ระดับความรู้ และอุปกรณ์ ไม่เก็บชื่อจริงในแบบบันทึกหลัก

## รูปแบบ Session

เวลา 40–45 นาทีต่อคน:

1. แนะนำและขอความยินยอม 3 นาที
2. Pre-test questions 4 นาที
3. Think-aloud ผ่าน 6 ภารกิจประมาณ 25 นาที
4. SUS 10 ข้อ 5 นาที
5. Debrief 5–8 นาที

ผู้ดำเนินการควรพูดว่า “เรากำลังทดสอบระบบ ไม่ได้ทดสอบคุณ” และไม่บอกชื่อเมนูหรือตำแหน่งปุ่ม หากผู้ใช้เงียบเกิน 10 วินาที ให้ถามเพียง “ตอนนี้กำลังคิดอะไรอยู่”

## ภารกิจ

### T1 — Natural-language Search

สถานการณ์: ต้องหาโน้ตบุ๊กสำหรับเขียนโปรแกรม งบไม่เกิน 30,000 บาท

สำเร็จเมื่อผู้ใช้พบผลลัพธ์ ระบุสินค้าอันดับแรกและราคาได้โดยไม่ช่วย เป้าหมาย ≤60 วินาที

### T2 — Understanding and Explanation

สถานการณ์: อธิบายว่าระบบเข้าใจความต้องการอะไรและทำไมอันดับแรกจึงถูกแนะนำ

สำเร็จเมื่อระบุได้อย่างน้อย 2 signals และเหตุผล 1 ข้อ โดยไม่ตีความ Match Score เป็น Accuracy เป้าหมาย ≤90 วินาที

### T3 — Refine, Filter and Sort

สถานการณ์: หาจอ 27 นิ้ว อย่างน้อย 144Hz เรียงราคาต่ำสุด ใช้ตัวกรองหนึ่งรายการ แล้วนำตัวกรองออก

สำเร็จเมื่อผลลัพธ์ หมวด Sort และ Filter เปลี่ยนสอดคล้องกัน เป้าหมาย ≤120 วินาที

### T4 — Ambiguity Recovery

สถานการณ์: เริ่มด้วยคำค้น “เอาไว้เล่นเกม” แล้วเดินหน้าต่อเพื่อหา Gaming Laptop

สำเร็จเมื่อเข้าใจว่าระบบขอข้อมูลเพิ่ม เลือกหมวด และได้ผลลัพธ์ถูกหมวด เป้าหมาย ≤90 วินาที

### T5 — Compare and Decide

สถานการณ์: เลือก Gaming Laptop สองรุ่นมาเปรียบเทียบและอธิบาย Trade-off

สำเร็จเมื่อเพิ่มสินค้ากลุ่มเดียวกัน เปิด Compare และอ้างอย่างน้อย 2 ด้าน เช่น ราคาและสเปก เป้าหมาย ≤150 วินาที

### T6 — Prototype Trust

สถานการณ์: ตรวจว่าราคาเป็นราคาปัจจุบันหรือไม่ และ Benchmark หมายถึงความแม่นยำกับทุกคำค้นหรือไม่

สำเร็จเมื่อตอบว่าเป็นข้อมูลสาธิต/อาจไม่ปัจจุบัน และ Benchmark จำกัดที่ curated scenarios พร้อมหาหลักฐานในหน้าได้ เป้าหมาย ≤120 วินาที

## การจัดผลต่อภารกิจ

- **Independent:** สำเร็จโดยไม่มี Hint
- **Assisted:** สำเร็จหลังได้รับ Hint
- **Fail:** ไม่สำเร็จ ผิดเป้าหมาย หรือเกิน 4 นาที

ข้อมูลที่บันทึก:

```text
Participant ID | Device | Tech level | Task | Start | End | Time
Result (I/A/F) | Query | Path | Misclicks | Backtracks | Hints
Hesitation | Expected vs observed | Quote | Confidence 1–5
Issue ID | Severity | Evidence
```

## SUS Questionnaire

ให้คะแนน 1 = ไม่เห็นด้วยอย่างยิ่ง ถึง 5 = เห็นด้วยอย่างยิ่ง

1. ฉันคิดว่าอยากใช้ระบบนี้บ่อยเมื่อต้องค้นหาสินค้าไอที
2. ฉันพบว่าระบบนี้ซับซ้อนเกินความจำเป็น
3. ฉันคิดว่าระบบนี้ใช้งานง่าย
4. ฉันคิดว่าต้องมีคนช่วยจึงจะใช้ระบบนี้ได้
5. ฉันพบว่าส่วนต่าง ๆ ของระบบทำงานเชื่อมโยงกันดี
6. ฉันพบว่าระบบนี้มีความไม่สอดคล้องกันมาก
7. ฉันคิดว่าคนส่วนใหญ่จะเรียนรู้ระบบนี้ได้เร็ว
8. ฉันพบว่าระบบนี้ใช้งานยุ่งยาก
9. ฉันรู้สึกมั่นใจขณะใช้ระบบนี้
10. ฉันต้องเรียนรู้อะไรมากก่อนจะใช้ระบบนี้ได้

Scoring: ข้อคี่ = คำตอบ − 1, ข้อคู่ = 5 − คำตอบ จากนั้นรวมและคูณ 2.5

คำถาม Diagnostic เพิ่มเติม 1–5:

- ผลลัพธ์แรกหาเจอง่าย
- ฉันเข้าใจว่าระบบตีความคำค้นอย่างไร
- เหตุผลจัดอันดับช่วยตัดสินใจ
- ฉันแยก Match Score ออกจาก Accuracy ได้
- ขอบเขตและข้อจำกัดสื่อสารตรงไปตรงมา

## Severity

- **P0 Blocker:** ทำภารกิจหลักไม่ได้หรือทำให้ตัดสินใจผิดและไม่มีทางเลี่ยง
- **P1 Major:** หลายคนทำไม่สำเร็จหรือเข้าใจคะแนน/ราคา/ขอบเขตผิด
- **P2 Moderate:** สำเร็จได้แต่ช้า หลง ย้อนกลับ หรือขอ Hint
- **P3 Minor:** ถ้อยคำ ระยะห่าง หรือความเรียบร้อยที่ไม่ขัดภารกิจ

## Acceptance Thresholds

- Independent task completion รวม ≥85%
- T1 Search และ T5 Compare ≥90%
- ผู้ใช้อย่างน้อย 80% อธิบาย Query signals และเหตุผลอันดับแรกได้ถูก
- ผู้ใช้อย่างน้อย 80% ไม่ตีความ Match Score เป็น Accuracy
- ผู้ใช้อย่างน้อย 80% ทราบว่าราคาเป็นข้อมูล Static และ Benchmark ไม่ Generalize
- SUS median ≥75 และไม่มีกลุ่มอุปกรณ์ต่ำกว่า 68
- Diagnostic ทุกข้อ median ≥4/5
- ไม่มี P0 หรือ P1 ที่ยังไม่แก้
- Critical mobile tasks ไม่มี Horizontal overflow หรือ Control ถูกบัง

หากไม่ผ่าน ให้แก้ P0/P1 แล้ว Retest 3–5 คนด้วยภารกิจเดิมแต่เปลี่ยนชื่อสินค้าและงบเพื่อลด Learning effect

## Report Template

1. Study date, Build hash, Devices, Participants และ Objective
2. Executive summary: Pass / Conditional / Fail
3. ตาราง Task success, Assisted, Fail, Median time และ Threshold
4. Issue log: Evidence, Frequency, Severity, Recommendation, Owner และ Status
5. SUS median/range และเปรียบเทียบ Novice/Expert, Desktop/Mobile
6. Decision: Ship / Fix and Retest / Blocked

แยก “สิ่งที่สังเกตได้” ออกจาก “การตีความสาเหตุ” ในรายงานเสมอ
